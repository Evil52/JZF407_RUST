## 1. Обзор проекта

Проект — прошивка на Rust + Embassy для платы JZ-F407VET6 (STM32F407VE + DP83848 PHY). Реализует управление реле и двумя светодиодами через MQTT и HTTP. Код разделён на два крейта: `logic` (чистая логика без железа, юнит-тестируется на хосте) и firmware (no_std, bare-metal).

## 2. Найденные баги

### 2.1 (НИЗКИЙ) Race condition при сохранении реле — двойной signal

**Файл:** `src/web.rs`, строки 300–305  
**Файл:** `src/buttons.rs` (обработчик кнопок)

```
POST /relay/on  → OUTPUTS.set_relay(on) → persistence.save_relay(on) → RELAY_CHANGE.signal(on)
Кнопка S1       → OUTPUTS.set_relay(on) → persistence.save_relay(on) → RELAY_CHANGE.signal(on)
```

Проблема: между `OUTPUTS.set_relay()` и `persistence.save_relay()` нет атомарности. Если кнопка и HTTP-запрос срабатывают одновременно, возможна ситуация:
1. HTTP устанавливает реле в ON
2. Кнопка устанавливает реле в ON (значение не меняется)
3. persistence кнопки читает `AtomicBool` (ON), видит что состояние совпадает с кэшем — **не пишет**
4. persistence HTTP читает `AtomicBool` (ON) — **тоже не пишет**, потому что compare_exchange вернул Ok

Это не столько баг потери данных, сколько **лишний вызов signal**, но его последствия не критичны.

Более серьёзный сценарий (разные направления):
1. HTTP: relay = OFF
2. Кнопка: relay = ON  
3. HTTP: save_relay(OFF) — compare_exchange видит ON ≠ OFF, меняет кэш на OFF, пишет OFF
4. Кнопка: save_relay(ON) — compare_exchange видит OFF ≠ ON, меняет кэш на ON, пишет ON
5. RELAY_CHANGE.signal(true) — mqtt_task публикует ON ✓

В этом сценарии всё корректно благодаря AtomicBool::compare_exchange.

**Вердикт:** Race condition существует, но `compare_exchange` в persistence.rs защищает от потери данных. Проблема сводится к возможному двойному signal — mqtt_task опубликует одно и то же значение дважды. **Приоритет: низкий.**

### 2.2 (СРЕДНИЙ) TcpSocket::close() + Drop = возможный RST вместо FIN

**Файл:** `src/web.rs`, строки 294, 298, 316, 330

```rust
socket.close();  // graceful FIN
// ... socket выходит из области видимости
// Drop вызывает abort() → RST
```

Проблема: `embassy-net::tcp::TcpSocket::Drop` вызывает `abort()`, что отправляет RST. Если close() был вызван, но рукопожатие FIN ещё не завершилось к моменту выхода сокета из области видимости, abort() отправит RST и разорвёт соединение. Это может проявляться как ошибки `ERR_CONNECTION_RESET` в браузере при медленной сети.

**Степень влияния на практике — близка к нулю.** Все обработчики вызывают `socket.flush().await` ДО `close()`, а flush завершается только когда TX-буфер передан и подтверждён ACK. То есть тело ответа гарантированно доставлено браузеру до закрытия. Даже если FIN не успеет уйти до Drop, smoltcp не шлёт RST при удалении сокета — RST прилетит лишь в ответ на последующий пакет браузера (FIN/ACK), к этому моменту `fetch`/загрузка страницы уже успешно завершены. Эмпирически: добавление `close()` устранило проблему `ERR_CONNECTION_RESET`, которая была до фикса.

**Рекомендация:** Оставить как есть — `flush()` перед `close()` достаточно. Если нужен строго graceful FIN, добавить точку `.await` (yield) между `close()` и Drop, чтобы net_task успел передать FIN.

⚠️ **НЕ использовать `core::mem::forget(socket)`** — сокет хранит хэндл в `SocketSet` smoltcp, а RX/TX-буферы статические и переиспользуются на следующей итерации цикла. Утечка хэндла + повторное использование тех же буферов новым сокетом = алиасинг буферов и порча данных. `Timer::after(500ms)` после каждого ответа тоже не нужен — он сериализует и замедляет сервер без реальной пользы.

**Приоритет: низкий** (по факту влияния), формально оставлен как пограничный из-за неграциозного закрытия в редком тайминге.

### 2.3 (НИЗКИЙ) parse_form принимает prefix_len=0 и prefix_len>32

**Файл:** `src/web.rs`, строка 367

```rust
"prefix" => { cfg.prefix_len = val.parse::<u8>().ok()?; }
```

Значения 0 и >32 будут приняты и сохранены в EEPROM. При следующей загрузке конфигурации `smoltcp`/`embassy-net` может повести себя неожиданно (0 — без сети, 33–255 — невалидная маска). Валидация отсутствует.

**Рекомендация:** Добавить проверку `if prefix_len > 32 { return None; }`.

**Приоритет: низкий.**

### 2.4 (НИЗКИЙ) Отсутствие rate-limiting на HTTP endpoints

**Файл:** `src/web.rs`, все обработчики

`POST /relay/on`, `POST /save`, `POST /reboot` не имеют защиты от повторных запросов. Злоумышленник в локальной сети может:
- Циклически переключать реле (износ механического реле и EEPROM)
- Многократно перезагружать устройство
- Зафлудить EEPROM записями через `/save`

**Рекомендация:** Добавить минимальный rate-limit (например, 500ms между обработкой POST-запросов) на уровне web_task. Для простоты можно запоминать `Instant` последнего POST и игнорировать запросы, пришедшие слишком быстро.

**Приоритет: низкий** (требует злоумышленника в локальной сети).

### 2.5 (НИЗКИЙ) IWDG использует непрогнозируемый LSI-осциллятор

**Файл:** `src/watchdog.rs`, строка 9

```rust
let mut wdg = IndependentWatchdog::new(iwdg, 20_000_000); // 20s in µs
```

LSI-осциллятор STM32F407 имеет номинальную частоту 32 кГц, но реальная частота может варьироваться от 17 до 47 кГц (по даташиту) в зависимости от температуры и напряжения. Это означает, что реальный таймаут IWDG может быть от ~13 до ~37 секунд вместо ожидаемых 20.

**Рекомендация:** Откалибровать LSI по HSI/HSE при старте (измерить LSI относительно точного источника) и скорректировать prescaler/reload. Или использовать WWDG с тактированием от APB1 для более точного таймаута.

**Приоритет: низкий** (система всё равно перезагрузится, просто тайминг неточный).

## 3. Потенциальные улучшения

### 3.1 Архитектурные

#### 3.1.1 CRC для EEPROM-данных
Обе структуры (output state и network config) защищены только magic-байтами. При частичной записи (сбой питания во время записи в EEPROM) возможна ситуация, когда magic уже записан, а данные — частично. Добавление CRC16/CRC32 в конец каждого блока решило бы эту проблему. Цена: 2–4 дополнительных байта на блок.

#### 3.1.2 DHCP-клиент
Устройство использует только статический IP. Добавление DHCP (с fallback на статический адрес) упростило бы первоначальную настройку. Библиотека `smoltcp` поддерживает DHCP-клиент; `embassy-net` предоставляет необходимые абстракции.

#### 3.1.3 "Применить без перезагрузки" для сетевых настроек
Сейчас любое изменение конфигурации через веб-интерфейс требует перезагрузки. Можно применить новый IP-адрес "на лету" через `Stack::set_config()` (если API embassy-net это поддерживает) или пересоздать только сетевой стек без полной перезагрузки.

#### 3.1.4 mDNS / Zeroconf
Добавление mDNS-responder (`stm32-jzf407.local`) упростило бы обнаружение устройства в сети без знания IP-адреса. Библиотека `smoltcp` поддерживает mDNS. Цена: ~2–3 KB flash, фоновая задача.

#### 3.1.5 MQTT over TLS
Сейчас MQTT работает без шифрования. Для production-среды желателен TLS. Для STM32F407 это потребует:
- Программный TLS (ring/rustls) — медленно, но возможно для лёгких нагрузок
- Аппаратный crypto-ускоритель CRYP — есть в STM32F407, но требует драйвера
Цена: значительный объём flash (~50–100 KB для rustls).

#### 3.1.6 OTA-обновление прошивки
Возможность обновить прошивку по сети без физического доступа к SWD. Потребует:
- Второй слот во Flash (256 KB для второй копии прошивки)
- Bootloader, проверяющий подпись/CRC и переключающий слоты
- HTTP-endpoint для загрузки .bin файла

### 3.2 Код и безопасность

#### 3.2.1 Буферизация логов
Сейчас при отсутствии подключённого отладчика (`defmt-rtt` в `non-blocking` режиме) логи теряются. Добавление кольцевого буфера в CCM RAM (например, последние 4 KB логов) позволило бы читать последние сообщения при подключении отладчика или через HTTP-endpoint `/logs`. Цена: ~4 KB CCM RAM.

#### 3.2.2 Метрики и health-check
Добавить эндпоинты:
- `GET /health` — возвращает `200 OK` с uptime, счётчиками переподключений MQTT, состоянием линка
- `GET /metrics` — Prometheus-совместимый формат (счётчики команд реле, ошибок MQTT, перезагрузок)

Цена: ~2 KB flash, минимальный RAM на счётчики.

#### 3.2.3 Аутентификация на веб-интерфейсе
Сейчас любой в локальной сети может управлять реле. Для production:
- Добавить пароль (сохраняемый в EEPROM) и Basic Auth на все POST-endpoints
- Или API-ключ для MQTT-команд

#### 3.2.4 Graceful degradation при ошибках EEPROM
Сейчас при ошибке записи/чтения EEPROM (например, чип не отвечает) работа продолжается без сохранения состояния. Можно добавить:
- Повторные попытки с экспоненциальной задержкой
- Индикацию ошибки EEPROM через светодиод (специальный паттерн мигания) и MQTT-топик `stm32/error`
- Fallback-режим работы без EEPROM (с默认ными настройками)

#### 3.2.5 Улучшение обработки MQTT-сообщений
Сейчас при получении некорректного payload на известный топик (например, `stm32/relay` со значением `"maybe"`) сообщение молча игнорируется. Желательно публиковать диагностическое сообщение в `stm32/error` или логировать предупреждение.

### 3.3 Тестирование и CI/CD

#### 3.3.1 Интеграционные тесты на хосте
Сейчас тестируется только `logic` крейт. Можно добавить интеграционные тесты для:
- `outputs.rs` — мок пинов, проверка состояний
- `web.rs` — парсинг HTTP-запросов, `parse_form`, `url_decode`
- `eeprom.rs` — симуляция I²C-устройства

Большая часть `web.rs` не использует железо напрямую (кроме `TcpSocket`), но из-за зависимости от `embassy-net` не компилируется на хосте. Можно выделить чистую логику в отдельные функции.

#### 3.3.2 CI/CD pipeline
Добавить `.github/workflows/ci.yml`:
```yaml
- cargo test -p jzf407-logic
- cargo build --release
- cargo clippy -- -D warnings
- cargo fmt --check
```

#### 3.3.3 Clippy-проверки
Проверено: `cargo clippy --release` (firmware) и `cargo clippy -p jzf407-logic` — **0 предупреждений**, код clippy-чист.

Замечание про `logic/src/debouncer.rs:30-31` (приоритет `&` и `==`) **не подтвердилось и неверно по сути**: в Rust бинарный `&` имеет более высокий приоритет, чем `==` (в отличие от C, где наоборот). Поэтому `self.history & 0x0F == 0x0F` корректно парсится как `(self.history & 0x0F) == 0x0F`. Скобки можно добавить для читаемости, но это не баг и не повод для clippy-варнинга.

`let _ = socket.write_all(...)` в `web.rs` — намеренное игнорирование ошибки отправки (если клиент отвалился, логировать нечего). Clippy на это не ругается.

### 3.4 Производительность и память

#### 3.4.1 Оптимизация PAGE_HEAD
`PAGE_HEAD` (строка 20–59 в web.rs) занимает ~2.1 KB во flash и содержит минифицированный CSS. Можно уменьшить на ~15-20% удалив неиспользуемые CSS-правила или используя более короткие имена классов (но ценой читаемости).

#### 3.4.2 HTTP keep-alive
Сейчас каждый HTTP-запрос открывает новое TCP-соединение. При опросе `/state` каждые 1.2 секунды это создаёт ~50 соединений в минуту. Поддержка `Connection: keep-alive` уменьшила бы накладные расходы на TCP handshake. Цена: усложнение цикла обработки запросов (нужно читать несколько запросов в одном соединении).

#### 3.4.3 WebSocket вместо polling
Сейчас веб-страница опрашивает `/state` каждые 1.2 секунды. WebSocket позволил бы серверу пушить изменения мгновенно без лишнего трафика. Но это значительно усложнит HTTP-сервер.

## 6. Итоговая оценка

**Качество кода:** Высокое. Код хорошо структурирован, документирован, разделён на платформо-независимую и аппаратную части. Комментарии осмысленны и объясняют неочевидные решения (Nagle, graceful FIN, grace period для retained MQTT). Bring-up notes в README демонстрируют глубокое понимание аппаратных особенностей STM32F407.

**Надёжность:** Выше среднего для embedded-проекта. Критических багов не обнаружено. Система корректно обрабатывает: потерю связи, перезагрузки, сбои EEPROM, зависания (через IWDG). Основной риск — неточный таймаут watchdog + отсутствие CRC в EEPROM.

**Безопасность:** Минимальная — достаточная для изолированной промышленной сети. Не рекомендуется для установки в сетях с недоверенными узлами без добавления аутентификации и rate-limiting.

**Готовность к production:** 7/10. Можно использовать в контролируемой среде. Для промышленного применения рекомендуется добавить CRC в EEPROM, rate-limiting и аутентификацию.

**Технический долг:** Низкий. Код чистый, без TODO/FIXME, без дублирования, с хорошим разделением ответственности.
